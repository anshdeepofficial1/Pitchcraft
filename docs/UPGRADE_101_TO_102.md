# Updating Pitchcraft 1.0.1 without losing People indexing

**Do not uninstall the installed app, clear its storage, or run `adb install -r -d` or `pm uninstall`.** The database contains scanned faces, embeddings, named People clusters and progress. A successful GitHub Actions build does **not** imply that Android will accept it as an update.

## What the source history proves

- `1.0.1`: versionCode `2`. The debug build used `com.anshdeep.pitchcraft.debug`, while release used `com.anshdeep.pitchcraft`.
- `1.0.2`: versionCode `3`, same two package IDs.
- GitHub's ordinary Android CI builds a **debug APK**. Each fresh GitHub-hosted runner can generate a *different* default `debug.keystore`, so its debug APK cannot reliably update a debug APK generated by a previous runner. The CI artifact is explicitly marked **TEST ONLY**.
- The only Android-supported in-place upgrade uses the **same package ID**, an **eligible versionCode**, and a **compatible original signing certificate/lineage**. Renaming an APK or modifying Gradle alone does not solve missing signing keys.
- The Room database is `pitchcraft_gallery_v1.db`. The v26→v27 People metadata migration is implemented, and destructive migration fallback is now disabled so incompatible databases are not silently erased.

## First: inspect what is actually installed (Windows)

Connect the phone, enable USB debugging, open PowerShell and run:

```powershell
adb devices
adb shell pm list packages | findstr pitchcraft
```

To inspect the installed APK certificate (its **public fingerprint**, not the secret private key):

```powershell
adb shell pm path com.anshdeep.pitchcraft.debug
```

Replace the package with `com.anshdeep.pitchcraft` if that is what's installed. Pull the indicated `base.apk` using `adb pull "<path from pm path>" old-1.0.1.apk`. Android may restrict APK pulling on some devices. Once you have the old APK, Android SDK's `apksigner verify --print-certs old-1.0.1.apk` shows the SHA-256 certificate fingerprint.

The helper below checks the **installed APK** against a candidate without changing phone data:

```powershell
.\scripts\check-android-upgrade.ps1 -NewApk "C:\path\Pitchcraft-1.0.2.apk"
```

Or supply the real installed baseline APK if your phone disallows pulling:

```powershell
.\scripts\check-android-upgrade.ps1 -NewApk "C:\path\Pitchcraft-1.0.2.apk" -OriginalApk "C:\path\old-1.0.1.apk"
```

The script rejects package, certificate and versionCode mismatches and never installs or uninstalls anything.

## Produce the **actual** in-place upgrade APK

1. Recover the **same keystore and signing alias that signed the installed 1.0.1**. If 1.0.1 was built on your Windows laptop with the default debug key, check `%USERPROFILE%\.android\debug.keystore`. If 1.0.1 came from an ephemeral GitHub Actions runner and its private keystore was never saved, its key usually cannot be reconstructed from an APK. **Never generate a replacement key and pretend it matches.**
2. Add these encrypted GitHub Actions *repository secrets* (never commit or send them in chat):
   - `PITCHCRAFT_KEYSTORE_BASE64`: base64 of the actual original keystore file. In PowerShell: `[Convert]::ToBase64String([IO.File]::ReadAllBytes("C:\path\old-signing-key.jks"))`.
   - `PITCHCRAFT_STORE_PASSWORD`: the original keystore password.
   - `PITCHCRAFT_KEY_ALIAS`: the exact alias.
   - `PITCHCRAFT_KEY_PASSWORD`: the original key password.
3. In GitHub → Actions → **Pitchcraft 1.0.2 In-Place Upgrade (Original Signing Key)** → Run workflow, choose the **installed** package ID. Enter the certificate SHA-256 fingerprint **from 1.0.1** in `original_cert_sha256`.
4. The workflow builds exactly **one** universal APK, verifies its signature cryptographically, checks the precise package ID and versionCode, and **refuses to upload** an incompatible result. Download its `Pitchcraft-1.0.2-verified-inplace-upgrade` artifact if the job succeeds.
5. Run `check-android-upgrade.ps1` before installation. Only if the package, signer and version check passes, use `adb install -r "C:\path\Pitchcraft-1.0.2.apk"` without any uninstall. Check existing People names and scan progress after the update.

**If the original key is lost:** a normal in-place Android update is technically impossible without an authorized signing lineage. Keep 1.0.1 installed. If it is a debuggable build, `adb shell run-as com.anshdeep.pitchcraft.debug id` may enable a local, user-controlled backup of its app-private data, but do not delete anything until the backup and recovery path are verified.

## Release and CI policy

- `.github/workflows/android.yml`: disposable debug-only emulator test; not an update artifact.
- `.github/workflows/release-apk.yml`: original-key upgrade build; requires original signer and original public certificate fingerprint.
- No workflow publishes a purported *upgrade-compatible* APK before the exact signer, package and version checks pass.
